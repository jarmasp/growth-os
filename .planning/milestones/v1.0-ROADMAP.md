# Roadmap: Engineering Growth OS

## Overview

Three infrastructure phases build the system from scratch — vault scaffold, seeded knowledge
graph, deliberate practice habits. After Phase 3, the system runs on autopilot: every
cashea-backend ticket becomes a learning artifact without extra cognitive load. Milestone 2.0
adds domain mastery paths once the core habit is stable.

## Milestones

- 🚧 **Milestone 1.0 — Growth OS Live** - Phases 1-3 (in progress)
- 📋 **Milestone 2.0 — Domain Mastery Underway** - Phases 4+ (planned after 1.0)

---

## Milestone 1.0 — Growth OS Live

**Goal:** The system runs. Every ticket leaves a reflection note. Every reflection links to
concept articles. Weekly review happens every week.

**Success criteria:** Jose completes one full sprint cycle (2 weeks) using the complete
system — pre-mortem before coding, reflection at ticket close, concept articles linked,
weekly review written — without the system feeling like extra work.

- [ ] **Phase 1: Vault Foundation** - Scaffold, templates, plugins, and Claude skills — everything needed to start capturing

## Phase Details

### Phase 1: Vault Foundation
**Goal**: Jose can close a cashea-backend ticket and write a complete reflection note in under 2 minutes, with correct structure, tags, and wikilinks — without making any decisions about where things go.
**Depends on**: Nothing (first phase)
**Requirements**: VAULT-01, VAULT-02, VAULT-03, VAULT-04, VAULT-05, VAULT-06, CAPT-01, CAPT-02, CAPT-03, CAPT-04, CAPT-05, CAPT-06, REFL-01, REFL-02, REFL-03, REFL-04, SKILL-01, SKILL-02, SKILL-03
**Success Criteria** (what must be TRUE):
  1. Vault folder structure exists at `Personal/Cashea/` with all 7 numbered directories
  2. All 8 plugins installed and configured in the correct order (Templater first)
  3. Vault is a private git repo (`cashea-knowledge-vault`), separate from cashea-backend, with 30-min auto-commit active
  4. Concept article template and ticket reflection template exist in `99-templates/` — a new note from template requires zero decisions about structure
  5. Weekly review template exists with Dataview queries pulling recent tickets and learning-gap concepts automatically
  6. Survival-mode weekly review (3-question) exists as a standing template
  7. `deslop` and `review-pr` Claude Code skills are active in `.claude/get-shit-done/skills/`
  8. Jose writes one real ticket reflection using the template and it takes under 2 minutes
**Plans**: 4 plans

Plans:
- [x] 01-01-PLAN.md — Vault scaffold: create folder structure, initialize git repo with remote, migrate 7 existing notes
- [ ] 01-02-PLAN.md — Plugin config: pre-write data.json for 4 installed plugins, manual install of 4 missing plugins
- [ ] 01-03-PLAN.md — Templates + taxonomy: create 5 templates, tag taxonomy, workflow rules
- [ ] 01-04-PLAN.md — MOCs + skills: create 6 MOC files with Dataview queries, verify Claude Code skills

### Phase 2: Knowledge Seed
**Goal**: The Obsidian graph has enough nodes that ticket reflections can always link to an existing concept — no reflection is ever orphaned because the concept article doesn't exist yet.
**Depends on**: Phase 1
**Requirements**: SEED-01, SEED-02, SEED-03
**Success Criteria** (what must be TRUE):
  1. ~40 concept article stubs exist in `10-concepts/`, one per architectural pattern and technology used in cashea-backend
  2. The 10 most-used concepts have full articles (all 6 sections complete, not just title + one-liner)
  3. Every article — stub or full — has at least 2 wikilinks to related concepts; graph view shows a connected graph, not isolated nodes
  4. A new ticket reflection can link to at least one existing concept article without creating a stub first
**Plans**: 3 plans

Plans:
- [x] 02-01-PLAN.md — Concept stub generation: create 39 concept stubs across backend/, system-design/, security/, infra/ with D-01 partial template format
- [x] 02-02-PLAN.md — Top-10 full articles: promote 10 stubs to full 6-section articles with code snippets from cashea-backend codebase
- [x] 02-03-PLAN.md — Graph wiring: audit all files for orphan nodes, link pre-existing files, verify connected graph in Obsidian

### Phase 3: Habits & Resources
**Goal**: Deliberate practice routines and domain reading resources are embedded in the workflow — the pre-mortem runs before every non-trivial ticket, the PR rewrite runs once per sprint, and domain books are queued with clear priority order.
**Depends on**: Phase 2
**Requirements**: LRNG-01, LRNG-02, LRNG-03, LRNG-04, PRAC-01, PRAC-02, PRAC-03, PRAC-04, PRAC-05
**Success Criteria** (what must be TRUE):
  1. Domain reading queues exist in `40-resources/` for all 6 domains (coding patterns, system design, GCP/infra, DevOps, observability, communication) — one active book per domain, others queued in priority order
  2. Podcast and video recommendations documented per domain (top 3 each), linked from the relevant MOC
  3. Obsidian resource notes created for all initial book recommendations (title, author, domain, why relevant, concept article links)
  4. Homework log exists in Obsidian with Tasks plugin tracking (`[ ]` pending, `[/]` in-progress, `[x]` done)
  5. Ticket pre-mortem section is in the ticket reflection template and Jose has run it on at least one real ticket (business context + 3 failure points + design pattern named)
  6. PR rewrite drill is documented as a recurring homework task in the homework log, scheduled once per sprint
  7. Naked system design exercise is documented as a recurring homework task, scheduled biweekly
**Plans**: 3 plans

Plans:
- [x] 03-01-PLAN.md — Domain resource notes: create 6 domain queue indices + 15 book resource notes in 40-resources/, podcast/video recs per domain, backfill concept article resource sections, link from MOCs
- [x] 03-02-PLAN.md — Homework log + recurring drills: create homework-log.md at vault root with 3 recurring drill tasks (PR rewrite, naked system design, one-concept deepening) + 1 one-off task
- [x] 03-03-PLAN.md — Practice habits in templates: add Pre-mortem and Assumptions sections to ticket-reflection.md, replacing placeholder comment

## Milestone 2.0 — Domain Mastery Underway

**Goal:** The growth OS is stable for 6+ weeks. Domain learning paths are active, GCP/ACE
exam preparation is structured, and the weekly review consistently surfaces capability
assertions Jose can point to.

**Notes:** Phases for this milestone are planned after Milestone 1.0 is complete and the
system has run for at least one full sprint cycle. Expected shape: one phase per domain
learning path activation (system design exercises, GCP ACE structured path,
observability instrumentation), plus a phase for advanced vault integrations (QuickAdd,
Advanced URI) once the core habit is stable.
